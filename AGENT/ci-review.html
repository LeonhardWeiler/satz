1. Playwright ist CPU-gebunden – mehr Worker helfen nicht

46 % der Laufzeit

Die Suite verbraucht ≈1230 CPU-Sekunden, ≈14 pro Test. 83 % davon im GPU-Prozess: Swiftshader rendert WebGL (CanvasKit) in Software. Renderer/WASM ≈ 5 %, Node ≈ 2 %. Die App ist nicht schuld: kein Dauer-Render-Loop, antialias ist aus, der Seitenstart kostet ≈0,6 s. Die Tests sind gleichmäßig (Ø 2,3 s, kein Ausreißer); pdf.spec.ts allein ist 21 % der Zeit.

auf 4 Kernen (simuliert)LaufzeitErgebnis
2 Worker (heute)245 s89 grün

2 Worker, --disable-gpu-compositing230 s89 grün, −6 %, im Rauschen

Auf einem Runner ist die CPU also voll. Schneller wird es nur mit mehr Kernen, d. h. mehr Runnern.

Lösung: e2e in 3 Shards auf eigenen Runnern (Matrix) und fullyParallel: true in playwright.config.ts, damit nicht ganze Dateien wie pdf.spec.ts an einem Shard hängen. Lokal mit --fully-parallel alle 89 grün; Shards auf 4 Kernen: 95 s / 79 s / 124 s.
Gewinn: 5:14 → ≈ 2:40 (längster Shard inkl. ≈40 s Setup), auf dem kritischen Pfad ≈ −2:30. Mehr Tests skalieren über die Zahl der Shards an einer Stelle.

2. Kein Rust-Cache: jeder Run kompiliert alle Crates dreimal kalt

3:16 min

clippy (check-Profil), Tests (test-Profil) und wasm (release, LTO) bauen jeweils alle Abhängigkeiten (loro, krilla, harfrust, tiny-skia …) neu. Lokal: wasm kalt 51 s, mit gecachten Abhängigkeiten nach einer Engine-Änderung 13 s (davon 7 s wasm-opt).

Lösung: actions/cache@v6 auf ~/.cargo/registry, ~/.cargo/git und target, Key cargo-${{ hashFiles('Cargo.lock', 'flake.lock') }} ohne restore-keys, dazu CARGO_INCREMENTAL: 0. Der Cache wird einmal pro Lockfile- bzw. Toolchain-Stand geschrieben und wächst nicht; nur die Engine selbst wird jedes Mal gebaut.
Gewinn: ≈ 3:16 → ≈ 1:10 inkl. ≈20 s Cache-Restore (Schätzung aus lokalem Faktor ≈4 für wasm).

3. Rust-Tests laufen unoptimiert

74 s → ≈6 s

a_placed_image_fills_a_rectangle_at_300_ppi_or_smaller_to_fit_its_page kodiert und dekodiert ein Bild mit 60000 × 3000 px im Debug-Build: 72 s in CI, 48 s lokal. a_saved_booklet_loads_as_it_was_without_undo_history braucht weitere ≈20 s. Nur Abhängigkeiten optimieren ([profile.dev.package."*"]) reicht nicht: 17 s, weil die Arbeit in der Engine selbst steckt.

Lösung: in Cargo.toml 
[profile.test]
opt-level = 1
Gilt nur für cargo test; cargo build und wasm bleiben gleich. Lokal gemessen: alle Tests 51 s → 4 s, inkrementeller Test-Build nach einer Engine-Änderung 2,3 s → 5,9 s.
Gewinn: ≈ −68 s in CI, lokal ≈ −47 s pro ./check. Kein Test entfällt, keine Testdaten ändern sich.

4. Dev-Shell lädt 2,4 GiB, die nie benutzt werden

54 s → ≈25 s

playwright-driver.browsers bringt Firefox (1,0 GiB), WebKit (1,1 GiB, mit GStreamer/PipeWire) und das volle Chromium (0,7 GiB) mit; gebraucht wird nur chromium-headless-shell. rust-bin…default enthält rust-docs (0,7 GiB). Mit Shards zahlt jeder Runner diesen Download.

Lösung: in flake.nix 
rust = pkgs.rust-bin.stable.latest.minimal.override {
  extensions = [ "clippy" "rustfmt" "rust-src" "rust-analyzer" ];
  targets = [ "wasm32-unknown-unknown" ];
};

PLAYWRIGHT_BROWSERS_PATH = pkgs.playwright-driver.browsers.override {
  withChromium = false;
  withFirefox = false;
  withWebkit = false;
};
Lokal gemessen: Closure 4,5 → 2,1 GiB; cargo fmt, clippy und e2e laufen damit grün.
Gewinn: ≈ −30 s pro Job (Schätzung, proportional zur Downloadgröße), bei 4 Jobs ≈ −2 min Runner-Zeit.

5. Alles in einem seriellen Step

Fehler erst nach ≈11 min

Ein e2e-Fehler zeigt sich erst am Ende, die GitHub-Oberfläche zeigt keine Zeiten pro Phase, und nichts läuft parallel. Die Kette selbst muss zusammenbleiben: tsc braucht die Typen aus wasm-pack, vitest braucht web/src/testdata/ aus cargo test. Nur e2e ist abtrennbar; es braucht allein web/dist.

Lösung: check bleibt die eine Stelle für alle Schritte und bekommt eine Stufe als Argument: ohne Argument alles wie heute, build alles bis pnpm build, e2e nur pnpm install und pnpm e2e mit den restlichen Argumenten. 
jobs:
  build:
    env: { CARGO_INCREMENTAL: 0 }
    steps:
      - checkout, install-nix-action, actions/cache (siehe #2)
      - run: nix develop -c ./check build
      - uses: actions/upload-artifact@v7   # name: dist, path: web/dist
      - uses: actions/upload-pages-artifact@v5
  e2e:
    needs: build
    strategy: { matrix: { shard: [1, 2, 3] } }
    steps:
      - checkout, install-nix-action
      - uses: actions/download-artifact@v8   # name: dist, path: web/dist
      - run: nix develop -c ./check e2e --shard=${{ matrix.shard }}/3
  deploy:
    needs: e2e
    …
Gewinn: kritischer Pfad ≈ build 2:30 + längster Shard 2:40 + Deploy 0:15 ≈ 5:30 statt 11:50. Rust- und Lint-Fehler zeigen sich nach ≈2 min.

6. CI läuft nur von Hand

kein Tempo, aber Risiko

Seit 1d614a7 nur workflow_dispatch: Commits auf main werden weder geprüft noch deployt, bis jemand den Run startet.

Lösung: nach #1–#5 wieder push: branches: [main] mit concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }, damit schnelle Folge-Commits ältere Runs abbrechen statt sich zu stauen.
